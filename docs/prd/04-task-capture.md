# 04｜待办录入与承诺快照

## 1. 目标

让用户用最少字段录入待办，并保留用户决定、AI 建议和正式日程之间的清晰边界。

## 2. 用户最少输入

创建任务必填：

1. `title`：要做什么；
2. `dueAt`：DDL；
3. `importance`：重要性。

AI 可建议但不要求用户先填：任务类型、预计时长、认知负荷、可拆分性。紧急性由系统结合当前时间和 DDL 计算，不要求用户重复填写。

用户提交这三个字段后，客户端必须先创建正式 `Task`，随后自动发起该任务的 AI 分析并进入“AI 建议确认”页面。任务列表不提供逐条“交给 AI 分析”入口；分析失败不回滚已创建任务。

## 3. 数据模型

```ts
interface Task extends ContractHeader {
  userId: UserId;
  title: string;
  dueAt: UTCTimestamp;
  importance: Importance;
  urgency: Urgency;                // 派生缓存，可重算
  status: TaskStatus;
  category?: TaskCategory;
  estimatedDurationMs?: DurationMs;
  cognitiveLoad?: CognitiveLoad;
  splittability?: Splittability;
  fieldOrigins: Record<string, "USER" | "AI_ACCEPTED" | "SYSTEM_DERIVED">;
  analysisProposalId?: EntityId;
  completedAt?: UTCTimestamp;
  actualFocusedDurationMs?: DurationMs;
  parentTaskId?: EntityId;
}
```

标题长度建议 1–120 字符。不得把窗口标题或截图内容自动写入任务标题。

## 4. 紧急性计算

紧急性不是用户优先级的替代品。建议默认阈值由策略数据集配置：

```text
dueAt < now                         → OVERDUE
remaining <= estimatedDuration+2h  → URGENT
remaining <= 3d                    → UPCOMING
otherwise                          → NOT_URGENT
```

若尚无预计时长，`URGENT` 只使用固定时间阈值。阈值必须带 `policyVersion`，不能散落在 UI 代码中。

### 4.1 重要/紧急四象限投影

四象限只是解释层，不覆盖更细的原始枚举：

| 是否重要 | 是否紧急 | 投影条件 | 默认解释 |
|---|---|---|---|
| 是 | 是 | `importance ∈ {HIGH, CRITICAL}` 且 `urgency ∈ {URGENT, OVERDUE}` | 优先处理 |
| 是 | 否 | 高重要且不紧急 | 安排完整时间块 |
| 否 | 是 | 低/中重要且紧急 | 尽快完成、缩小范围或重新确认 |
| 否 | 否 | 低/中重要且不紧急 | 有余量再排 |

用户负责标注重要性；系统负责计算紧急性。系统不得因为 DDL 很近而静默把“重要性”改高。

## 5. 状态流转

```text
BACKLOG → PLANNED → IN_PROGRESS → COMPLETED
   ├──────────────→ CANCELLED
PLANNED ──────────→ CANCELLED
COMPLETED ── 用户撤销完成 ──→ IN_PROGRESS
```

- 完成必须记录 `completedAt`。
- 撤销完成要产生审计事件；若已结算奖励资格，不回写历史结算，进入人工/后续纠正流程。
- 删除采用软删除，已进入承诺快照的任务不可物理删除。

## 6. 用户优先规则

- 新建任务的首次 AI 分析自动触发，但 Proposal 仍不是正式字段；用户点击“确认建议”后才写入接受项。
- 用户修改 AI 建议字段后，`fieldOrigins` 改为 `USER`。
- 后续 AI 可提出新 Proposal，但不得静默覆盖 `USER` 字段。
- 用户可拒绝 AI 拆分；拒绝记录用于减少同类建议，不强迫解释原因。
- 日程中任务顺序可直接拖动，形成用户锁定约束。

## 7. 当日承诺快照

### 7.1 作用

冻结“今天承诺完成哪些任务”，用于每日胜利和加班奖励资格。它不是当前任务列表的动态别名。

### 7.2 生成建议

1. AI 日程草案生成后展示“今日承诺任务”。
2. 用户确认日程时同时确认承诺集合。
3. 未生成日程时，首次进入工作状态可弹出轻量确认。
4. 快照创建后仅允许追加；移除必须记录取消原因和资格影响。

`[待确认: TASK-COMMIT-001][阻塞]` 冻结时机。建议首次进入工作状态后 15 分钟内必须确认，逾期当天标记 `NO_COMMITMENT`，避免临近下班才挑已完成任务。

### 7.3 必要任务与可选任务

MVP 建议快照只包含“必要任务”。若将来加入可选任务，必须单独字段表示，不能用状态猜测。

## 8. 实际时长反馈

- 用户开始/暂停任务可累积显式专注时长。
- 活动识别可提供辅助区间，但不能把所有键盘时间自动归到某任务。
- 完成时允许用户确认“实际大约用了多久”。
- 训练使用的数据必须保存来源和置信度：显式计时 > 用户回填 > 系统推断。

## 9. 失败模式

- DDL 早于当前时间：允许创建并标记 `OVERDUE`，明确提示。
- DDL 与时区转换失败：阻止保存，要求用户修正。
- 版本冲突：返回最新任务和字段差异，不直接覆盖。
- 离线创建：使用本地临时 ID 排队；同步后建立 ID 映射。
- 自动 AI 分析失败：保留已创建任务并停留在建议确认页展示重试/确定性基线，不在任务列表增加逐条分析按钮。
- 重复点击完成：幂等，不重复写完成事件。

## 10. 验收条件

1. 只填标题、DDL、重要性即可创建任务，并自动进入该任务的 AI 建议确认页。
2. 任务列表不存在逐条“交给 AI 分析”入口。
3. 未经用户点击“确认建议”，AI 不改变正式任务字段。
4. 用户改过的预计时长不会被下一次分析静默覆盖。
5. 紧急性随时间和 DDL 重算，不要求用户填写。
6. 已进入承诺快照的任务删除后仍可审计。
7. 结算资格读取冻结快照，而不是结算时当前任务列表。
8. 离线创建和恢复同步不产生重复任务。

## 11. 待确认项

`[待确认: TASK-COMMIT-001]` 承诺冻结时机与迟到处理。  
`[待确认: TASK-001]` 是否允许无 DDL 的长期任务。当前需求要求 DDL，建议 MVP 不允许。  
`[待确认: TASK-002]` 撤销“已完成”是否影响尚未执行的当日结算。建议截止前实时影响，结算完成后不追溯。
